# 11. Security Plan

> Status: Draft v0.2 · Owner: Laxman Sirvi · Last updated: 2026-10-11

This plan explains how the application is secured through development and production. The short, mandatory rules that code must obey are in [SECURITY_RULES.md](../SECURITY_RULES.md). AI-specific threats are in [14-AI-security-and-privacy.md](14-AI-security-and-privacy.md).

## 1. Assets

| Asset | Why it matters |
| --- | --- |
| Student records (marks, attendance, results, contact details) | Personal and academically sensitive. Integrity matters as much as confidentiality. |
| Credentials (password hashes, sessions) | Give access to everything above. |
| Secrets (database password, Supabase service key, AI key) | Full control of data, files and spend. |
| Question bank answers | Leaking them makes tests meaningless. |
| Learning resources | College material; must not be publicly crawlable. |
| Audit log | Evidence of who changed what. |
| AI budget | Real money; can be drained by abuse. |

## 2. Threat model

| # | Threat | Example | Main controls |
| --- | --- | --- | --- |
| T1 | Reading another student's records | Changing an ID in a request | `/me` endpoints, ownership in queries (§5) |
| T2 | Student changes official data | Posting to a marks endpoint | No student write endpoints; role checks (§5) |
| T3 | Password guessing | Trying common passwords | BCrypt, lockout, rate limit (§3, §8) |
| T4 | Session theft or fixation | Stolen cookie; shared computer | Cookie flags, session rotation, timeout (§4) |
| T5 | Cross-site request forgery | Hidden form on another site | CSRF tokens, `SameSite` (§7) |
| T6 | Cross-site scripting | Script in a notice or AI answer | Text-only rendering, CSP (§7) |
| T7 | SQL injection | Crafted search text | Bound parameters only (§6) |
| T8 | Malicious upload | Executable renamed `.pdf` | Upload validation (§9) |
| T9 | Leaked secrets | Key committed to GitHub | Secrets management (§11) |
| T10 | Public exposure through Supabase | Data API or public bucket | Data API off, unexposed schema, no grants, RLS, private bucket (§10) |
| T11 | Abuse and cost | Scripted AI calls | Quotas and rate limits (§8) |
| T12 | Vulnerable dependency | Known CVE in a library | Dependency management (§12) |
| T13 | Information leakage | Stack trace in an error | Global handler, logging rules (§13) |
| T14 | Tampering with evidence | Editing the audit log | No update or delete privilege, triggers, separate credentials (§13) |
| T15 | Careless or over-permissioned coding agent | Destructive migration, leaked key | [AI_AGENT_SECURITY_RULES.md](../AI_AGENT_SECURITY_RULES.md) |
| T16 | Leaked database credential | Runtime password exposed | Least-privilege runtime role; separate migration role (§10) |

| T18 | Predictable temporary password | Logging in as a student who has not yet changed the roll-number password | Forced change before any access; exception limited to synthetic data (§3.4) |

Out of scope for a student project: denial-of-service at the network level, physical security, and compromise of Heroku or Supabase themselves.

## 3. Authentication and passwords

> Revised on 2026-10-11 for the owner's change request: login by institutional email, with the roll number as a new student's first password. The decision and its security exception are in [ADR 0008](decisions/0008-institutional-email-login.md). The architecture is unchanged: Spring Security, server-side sessions, BCrypt. No custom cryptography is written.

### 3.1 Login identity

- The login identifier of every account is its institutional email address, trimmed and converted to lower case before every lookup and write. Uniqueness is enforced by the database.
- A student's email is generated by the system from the roll number and the domain in `STUDENT_EMAIL_DOMAIN`. The domain is never hardcoded.
- The roll number stays in the student profile as the academic identifier. It is not accepted as a login identifier.
- **The email is an identifier, not a verified address.** The application sends no email and does not check that a mailbox exists or belongs to the student. Following the institutional pattern proves nothing about who is typing it.
- The session holds only the account ID and the role.

### 3.2 Password storage and rules

- Passwords are hashed with BCrypt (cost 10 or higher) through Spring's `PasswordEncoder`. No password, temporary or permanent, is ever stored or logged in plaintext.
- One class, `PasswordPolicy`, decides whether a new password is acceptable, and every path that sets a user-chosen password uses it:
  - 8 to 72 characters. BCrypt ignores input beyond 72 bytes, so longer input is rejected, not silently cut.
  - Ignoring letter case, not the user's roll number, not the user's email address, not the part of the email before the `@`, and not the current password.
- Login failures return one generic response for a wrong password, an email with no account and a deactivated account. The same hash comparison is performed when no account is found, so that response time does not give the answer away.
- Text that is not an email address is rejected as invalid input, decided from the text alone and therefore identical for every address.

### 3.3 Temporary passwords

| Situation | Temporary password | Shown or returned? |
| --- | --- | --- |
| A student is provisioned | The student's roll number, as stored (upper case) | **Never.** Not returned, not displayed, not logged as a password |
| An admin resets a student's password | Random, from `SecureRandom`, 12 characters or more | Once, to the admin who requested it |
| The first admin is created at startup | A strong password chosen by the owner, from configuration | No |

- Every temporary password sets `must_change_password`. While it is set, the server refuses every request except fetching the CSRF token, reading the current user, changing the password and logging out. This is a filter in the security chain, applied to every endpoint and page.
- After the change the temporary password no longer works. The policy means a roll number can never be chosen again.
- **Admin accounts never receive a roll-number password**, at creation or at any other time.

### 3.4 Security exception EX-AUTH-01: the roll number as a first password

This is a deliberate exception to the rule that a predictable value must not be a password. It is recorded here in full so that nobody mistakes it for a safe design.

**The weakness.** A student's email address contains their roll number, and the first password is that same roll number. Roll numbers are not secret: they are on identity cards, attendance sheets and class lists. So anyone who knows a roll number knows both halves of the credential.

**What can happen.** Until a student has changed the password, anyone can log in as that student, read their records, and choose a new password, which locks the real student out. An attacker with a class list could do this to every unclaimed account in minutes. Lockout does not help, because the first guess is correct.

**A consequence for logging.** The temporary password is not a secret, so the same characters appear in lists, API responses and logs as the roll number or inside the email. The rule "passwords never appear in logs" is kept in this sense: the password field of a request is never logged, and no value is ever logged, returned or audited *as a password*. It cannot make the roll number secret.

**Why it is accepted.** The owner requires this onboarding for the assignment and demonstration. All data is synthetic, so a takeover exposes no real person's records.

**Conditions. All are mandatory:**

1. Synthetic data only.
2. The password change is forced on the server before any other function.
3. Only a salted hash of the temporary password is stored.
4. The application never returns or displays the temporary password.
5. It applies to newly provisioned student accounts only. Never to admins.
6. An admin reset uses a random password, never the roll number.
7. A roll number can never be chosen as a password again.
8. Provisioning, password changes and resets are audited, with no password data.

**Recommended practice** (operational, not automated): provision accounts shortly before students first log in; review the list for accounts still awaiting first login and deactivate any that should not be open; if a student reports that their password was changed before they ever logged in, treat it as a takeover, reset the password and read the audit entry.

**Not approved for real students.** Before any deployment that holds real student data, the owner must carry out an explicit security review and record a new decision (OQ-17). Options to weigh then include random one-time passwords handed over in person, an activation step that needs a second fact, or the institution's own single sign-on.

### 3.5 Lockout and rate limits

- Five consecutive failed logins for an email address block further attempts for that email for 15 minutes.
- **The block applies whether or not an account exists**, with an identical response, so it reveals nothing. For real accounts the counter is stored in the database; for emails with no account it is kept in application memory with the same thresholds. This resolves open decision OQ-13.
- A successful login resets the counter. An admin reset clears a block.
- One IP address may make at most 20 login attempts in 10 minutes.
- Accepted side effect: someone can block a known student's email for 15 minutes by failing five times. The per-IP limit slows this down.

### 3.6 Provisioning, reset and deactivation

- **No self-registration.** Accounts are provisioned by an admin from the verified student roster, or by the approved import (P1). The application checks format and uniqueness; whether the roster is right is the admin's responsibility.
- **Reset.** A student who cannot log in asks an admin, who confirms their identity in person and uses "Reset password". The reset issues a random temporary password, ends the student's sessions, clears any block, forces a change at the next login, and is audited. There is no self-service or email reset, because the application sends no email.
- **Deactivate.** Ends the account's sessions at once. Login then gives the generic failure.
- **Reactivate.** Restores the account with the password it had. If the account was still awaiting its first login, that password is still the roll number, so the admin should reset it when in doubt.
- **Admin accounts** are provisioned separately with their own credentials.

## 4. Session management

| Setting | Value |
| --- | --- |
| Storage | Server memory (database-backed sessions are P1) |
| Cookie | `JSESSIONID`; `HttpOnly`, `Secure`, `SameSite=Lax`, path `/` |
| Idle timeout | 30 minutes |
| Fixation | Session ID is replaced at login |
| Logout | Session invalidated on the server; cookie cleared |
| Password change | The user's other sessions are invalidated and the current session gets a new identifier |
| Admin password reset | Every session of that user is invalidated at once |
| Deactivation | Every session of that user is invalidated at once |
| Concurrent sessions | Allowed (phone and lab computer) |
| Caching | `Cache-Control: no-store` on all API responses and protected pages |

The session holds only the user ID and role.

Ending another user's sessions uses Spring Security's session registry, which works because all sessions are held in one process. If sessions are moved to the database (P1), the same three rules must still hold.

## 5. Access control

Defined in [10-authorization-matrix.md](10-authorization-matrix.md). Principles:

1. **Deny by default.** Any request not matched by an explicit rule requires authentication.
2. **Roles from the server.** The role comes from the session, never from the request.
3. **Ownership in the query.** Student data is fetched by the session's student ID. Owned objects are fetched by "ID and owner".
4. **Same answer for missing and forbidden** (`404`), so IDs cannot be probed.
5. **Two layers for admin functions:** URL rules and method-level checks.
6. **Least data.** DTOs contain only the fields a screen needs. Entities are never serialized directly.

## 6. Input validation and injection

- Every request DTO is validated with Bean Validation: required fields, lengths, ranges, patterns and enums. Limits are in the API contract.
- Unknown JSON fields are rejected, which blocks mass-assignment of fields such as `role` or `studentId`.
- Database access uses Spring Data, JPQL or native queries with bound parameters. No SQL is built by concatenation, including `ORDER BY`: sort fields are checked against an allow-list.
- Search text is escaped for `LIKE` wildcards.
- File names from users are never used in paths.

## 7. Browser-side protections

### CSRF

Enabled for all state-changing requests, using a cookie-to-header token (`XSRF-TOKEN` cookie, `X-XSRF-TOKEN` header). CSRF protection is never disabled, including on login.

### XSS

- All dynamic text is inserted with `textContent`. `innerHTML` never receives server or AI data.
- Notices are plain text. No HTML or Markdown is accepted from admins or from the AI in the first release.
- No inline scripts or event-handler attributes.

### Security headers

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: https://<project>.supabase.co; frame-src https://<project>.supabase.co; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` (production) |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `Permissions-Policy` | camera, microphone and geolocation disabled |

`frame-src` allows only the project's storage host, for the PDF preview. `img-src` allows the same single host, for a student's own profile photo ([ADR 0009](decisions/0009-student-personal-details-and-photo.md)). The host is written into the header only when `SUPABASE_URL` is a plain `https://` host name; otherwise frames are not allowed at all and images come from the application only. No CORS configuration is needed because the frontend and API share one origin; cross-origin requests are not allowed.

Mermaid (P1, task `T7-05`) inserts inline styles, which `style-src 'self'` blocks. That task must propose the smallest policy change that works and get the owner's approval. The policy above is not loosened before then.

### Transport

HTTPS only. Heroku terminates TLS; the application trusts forwarded headers only from the platform and redirects HTTP to HTTPS in production.

## 8. Rate limiting and abuse

Implemented as a small in-memory limiter in Java (`RateLimitFilter`), which is enough for one dyno.

| Scope | Limit |
| --- | --- |
| Login, per IP address | 20 attempts per 10 minutes |
| Login, per account | 5 consecutive failures, then 15-minute lock |
| AI | Per-user per-minute and per-day limits, a concurrency limit and an application-wide daily ceiling. The values are defined once, in [12-AI-features-spec.md](12-AI-features-spec.md) §2 |
| Other API calls, per session | 120 per minute |
| Request body | 64 KB for JSON; 10 MB for uploads |

`AI_ENABLED=false` switches the assistant off immediately without a deployment.

## 9. Uploads

Only administrators upload. Even so, each file is treated as hostile:

1. Size limit of 10 MB, enforced by the server before the file is read into memory in full.
2. The declared content type and the extension must be PDF.
3. The first bytes must be the PDF signature (`%PDF-`).
4. The file is opened with PDFBox to confirm it parses; encrypted or unparseable files are rejected. Parsing has a page and time limit: at most 2,000 pages, and 10 seconds on one of two dedicated threads.
5. A SHA-256 checksum is stored.
6. The storage path is generated by the server from the subject code and a random UUID.
7. Files are stored in Supabase Storage, never on the dyno's disk and never under the application's own origin.
8. Files are served with `Content-Type: application/pdf` from the storage host, so a malicious file cannot run script in the application's origin.

There is no virus scanning in the first release. This is an accepted risk because uploaders are trusted staff and only PDFs are accepted.

### Profile photos

Since 2026-10-14 a student may upload one kind of file: their own profile photo ([ADR 0009](decisions/0009-student-personal-details-and-photo.md)). It is treated as hostile in the same way:

1. Size limit of 2 MB, checked from the request before the file is read.
2. The declared content type must be JPEG or PNG, and the first bytes must be the signature of that format. Anything else, including GIF and SVG, is refused.
3. The picture's width and height are read before it is decoded. A picture under 64 or over 6,000 pixels on a side is refused without being loaded, and a large one is decoded at reduced resolution, so a small file cannot fill the memory.
4. **The uploaded file is never stored.** The server draws the middle square of the picture at 512 by 512 pixels and writes a new JPEG. EXIF data, including the place and time a phone records, does not survive, and neither does anything else hidden in the file.
5. The storage path is `profile-photos/` and a random UUID. The API never returns it.
6. The photo is shown only to its owner, through a signed link that lasts five minutes.

### Student CSV import

An administrator may upload a CSV file of students (FR-ADM-010, [09-api-contract.md](09-api-contract.md) §8.14):

1. 1 MB at most, checked before the file is read; the name must end in `.csv`.
2. The bytes must be valid UTF-8; anything else is refused rather than guessed.
3. At most 100 students, so the request ends well inside the platform's 30 seconds; at most 100 problems are returned.
4. Every line goes through `StudentProvisioningService`, the same validation, email rule and audit entry as a student added by hand. Nothing is saved unless every line is valid, and all of it is one transaction.
5. **The file is never stored**, neither in the database nor in Storage. It is read in memory and dropped.
6. The first password of every imported student is the roll number (EX-AUTH-01), so the import is for synthetic data only until the owner answers OQ-17.

## 10. Supabase controls

### Database

The model is specified in [08-database-design.md](08-database-design.md) §11 and is Proposed in [ADR 0007](decisions/0007-database-roles-and-rls.md) (OQ-10). In summary:

- **The application is the authorization boundary.** The database cannot distinguish users, so it is never relied on for per-student access.
- **Two roles.** `cc_app` (runtime) reads and writes rows with the minimum privileges for each table and owns nothing. `cc_migrator` (Flyway) owns the schema. The application never connects as `postgres`. Both connect over TLS through the session pooler.
- **The Data API is closed three ways.** It is switched off; the tables are in schema `app`, which is not exposed; and `anon`, `authenticated` and `service_role` have no grants there.
- **RLS is a backstop, not the control.** It is enabled on every table with policies for `cc_app` only. It does not restrict the table owner or roles that bypass RLS (`service_role`, Supabase's `postgres`), and it does not separate one student from another.
- Supabase's public key and service key are never sent to the browser. The frontend has no Supabase client.
- Network restrictions on the database are enabled if the plan supports them.

Checks before release: the Data API is off; a Data API request with the project's public key returns no application data; `cc_app` owns nothing and cannot update `audit_logs`.

### Storage

- One **private** bucket. Public access is off.
- No storage policies grant access to `anon` or `authenticated` roles. Only the service key, held by the backend, can read or write.
- Signed URLs last at most five minutes and are issued only after the resource is confirmed published.
- Signed URLs are never logged or stored.

## 11. Secrets management

| Secret | Where it lives |
| --- | --- |
| Runtime database password, migration database password, Supabase service key, AI key, bootstrap admin password | Heroku config vars in production; an untracked `.env` file locally |

- `.env` is in `.gitignore`. `.env.example` contains names only.
- Secrets never appear in source code, tests, documents, commit messages, issue text or logs.
- Enable GitHub secret scanning and push protection on the repository. Checked on 2026-10-11: these, Dependabot security updates and private vulnerability reporting are **not yet enabled** (task `T0-04`).
- If a secret is exposed anywhere, it is rotated immediately (see the [runbook](19-operations-runbook.md)). Deleting the commit is not enough.
- Each environment has its own secrets. Production secrets are never used locally.
- The `postgres` administrative password is not part of the application's configuration at all. The owner keeps it in a password manager.

## 12. Dependency management

- All dependencies come through Maven with versions managed by the Spring Boot parent.
- Enable Dependabot alerts and security updates on GitHub.
- Before each release, review open alerts; any high or critical finding in a runtime dependency blocks the release until updated or explicitly accepted by the owner.
- New dependencies need approval (see [04-TRD.md](04-TRD.md) §14).
- Frontend libraries are vendored at a pinned version; none are loaded from a CDN.

## 13. Logging and audit

### Security logging

Logged with user ID, IP address and request ID: login success and failure, lockouts, password changes and resets, access-denied events, rate-limit hits, upload rejections, AI declines and failures.

Never logged: passwords, session IDs, CSRF tokens, API keys, signed URLs, or AI prompt and response text. The password field of a request is never logged at any level. Because a new student's temporary password is their roll number, a roll number will appear in logs as an identifier; it is never logged as, or beside, a password (§3.4).

### Audit trail

The audited actions, the permitted contents and the protections are specified in [08-database-design.md](08-database-design.md) §12. In summary:

- Changes to marks, attendance, semester results, profiles and account status, and password resets and changes, each write an `audit_logs` row in the same transaction as the change.
- Data changes record the old and new values of allow-listed fields. **Password events record no values at all.** No row ever holds a password, a temporary password or a password hash.
- The runtime database role can insert and read audit rows but cannot update, delete or truncate them, and triggers reject those statements for every role.
- The log is tamper-resistant against the application and its credential. It is not tamper-proof against a database administrator. That residual risk is accepted and recorded as R23 in the [risk register](20-risk-register.md).

### Errors

One global handler returns problem details with a `traceId`. Stack traces, SQL, class names and file paths stay in the server log.

## 14. Backup, incident response and recovery

- Backups: see [08-database-design.md](08-database-design.md) §10.
- Incident steps (what to do when a key leaks, an account is compromised, or data is wrong) are in [19-operations-runbook.md](19-operations-runbook.md).
- General order in an incident: **contain** (disable AI, rotate keys, deactivate accounts), **assess** (audit log, application logs), **recover** (restore or correct data), **record** (write a short note of what happened and what changed).

## 15. Security testing

Defined in detail in [17-testing-strategy.md](17-testing-strategy.md). Mandatory automated scenarios:

1. Every protected endpoint rejects a visitor (401).
2. Every admin endpoint rejects a student (403).
3. A student requesting another student's attempt, or any record by a foreign ID, gets 404.
4. A student cannot change marks or attendance through any endpoint.
5. State-changing requests without a CSRF token are rejected.
6. Login blocks an email after five failures, identically whether or not an account exists.
7. Uploads that are oversized, mis-typed or not real PDFs are rejected.
8. Quiz start responses contain no correct answers.
9. Error responses contain no stack traces.
10. Adversarial prompts do not reveal secrets or other users' data, and a reply that is well-formed but off-policy is still shown only as labelled plain text.
11. No audit row contains password material; password events have null values.
12. The runtime database role cannot update, delete or truncate audit rows.
13. The runtime database role owns no table and holds exactly the privileges listed in the database design.
14. A provisioned student can log in with the institutional email and the roll number, and can then do nothing except change the password, including through direct API calls.
15. After the change the roll number no longer works and cannot be chosen again.
16. No login response differs between an email that has an account and one that has not.
17. No password or hash appears in logs, in API responses other than the one-time reset response, or in audit rows.
18. The database rejects a duplicate or non-normalised login email and a duplicate roll number.

## 16. Release criteria

A release is blocked unless all of these are true:

- [ ] All mandatory security tests pass.
- [ ] No secret is present in the repository history (secret scanning clean).
- [ ] No open high or critical dependency alert without a recorded decision.
- [ ] The Data API is off, schema `app` is not exposed, and a Data API request with the public key returns no application data.
- [ ] The application connects as `cc_app`; RLS, grants and policies match the database design (database tests pass).
- [ ] GitHub secret scanning, push protection, Dependabot alerts and private vulnerability reporting are enabled.
- [ ] The storage bucket is private and an unsigned URL is refused.
- [ ] Production cookies are `Secure` and `HttpOnly`; HTTP redirects to HTTPS.
- [ ] Security headers are present on a production response.
- [ ] The bootstrap admin password has been changed.
- [ ] `STUDENT_EMAIL_DOMAIN` is the domain the owner confirmed (OQ-15).
- [ ] Exception EX-AUTH-01 applies: this deployment holds synthetic data only (OQ-17).
- [ ] No account is left awaiting first login that should not be open.
- [ ] Only synthetic data is loaded.
- [ ] Actuator exposes only `health`.

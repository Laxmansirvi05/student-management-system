# 0009. Students edit their personal details and upload a profile photo

- Status: Accepted by the owner's change request of 2026-10-14. Built and tested with synthetic data. The photo part has not been run against the real storage bucket yet (task `T3-01` is still open).
- Date: 2026-10-14
- Deciders: Laxman Sirvi
- Changes: FR-STU-002 (no longer fully read-only); adds FR-STU-003, FR-STU-004 and FR-LEG-001

> **Amended on 2026-10-18 at the owner's request:** a student may also keep a personal email, LinkedIn, GitHub and portfolio links, and a list of skills (V9). The same reasoning applies: these are the student's own details, not the college's record. Links are limited to https web pages without credentials, checked in Java (`ProfileLinks`) and by the database, so a link on the page cannot run script or carry a password.

## Context

Until now a student's profile was read-only, and the project said explicitly that there was no profile photo. Only administrators uploaded files, and only PDFs. On 2026-10-14 the owner asked for three things:

1. Students can edit their profile and add a photo.
2. A settings section where a user changes their password and "certain more details".
3. A privacy policy and terms and conditions.

The first point touches three things the project treats as sensitive: who may change a profile, who may upload a file, and the Content-Security-Policy header. This record says what was decided for each, so the owner can review it.

## Options considered

1. **Let the student edit every profile field.** Simple, but the name, roll number, branch, semester and section are the college's record. A student who can change them can misstate who they are and which class they are in, and the login email is derived from the roll number.
2. **Let the student edit personal details only, and keep the college's fields read-only.** The student gets something that is theirs to keep up to date; the record stays the college's.
3. **Keep the photo in the database or on the application server.** Forbidden by SR-31: uploads are never saved to, or served from, the application's own file system or origin.
4. **Keep the photo in the private storage bucket and show it through a signed link**, as study material already is.
5. **Store the uploaded photo file as it is.** A photo from a phone carries the place and time it was taken, and a hostile file can carry anything.
6. **Redraw the photo and store only the new picture.**

## Decision

Options 2, 4 and 6.

- **What a student may edit:** their phone number, a text of up to 280 characters about themselves, and a photo. Nothing else. The request body has fields for the phone and the text only; because the application refuses unknown fields, a request that names `fullName`, `rollNo`, `branch` or `role` is answered `400` and changes nothing.
- **Whose profile:** always the one of the logged-in student, taken from the session. The endpoints are under `/students/me` and accept no student identifier.
- **The photo upload** is checked like every upload (SR-27): at most 2 MB, declared as JPEG or PNG, the first bytes of that format, and it must open as a picture between 64 and 6,000 pixels on each side. The size of the picture is read before it is decoded, so a huge picture is refused without being loaded.
- **What is stored** is never the uploaded file. `ProfilePhotoProcessor` draws the middle square of the picture at 512 by 512 pixels and writes a new JPEG. The uploaded bytes are discarded, so EXIF data (place, time, device) and anything else hidden in the file do not survive. The orientation tag is read first, with every position checked, so that a phone photo stored on its side is turned upright.
- **Where it is stored:** in the private bucket, at `profile-photos/<random UUID>.jpg`. The path is generated by the server (SR-28) and contains nothing of the file name or of the student. The API tells the browser only that a photo exists (`hasPhoto`), never the path.
- **How it is shown:** through a signed link that lasts five minutes, issued only to the student whose photo it is (SR-30). Nobody else can ask for it in this release; an administrator does not see student photos.
- **Content-Security-Policy:** `img-src` gains the storage host, the same single validated host that `frame-src` already allows for the PDF preview. Without it the browser would refuse to show the photo. Scripts, styles and requests made by scripts still come from the application's own origin only.
- **Audit:** a changed phone number is written to the audit log as `PROFILE_UPDATED`, with the student as the actor. The text and the photo are not audited: they are the student's own words and picture, not a record.
- **Settings:** a page in each portal with the existing change-password function, a "Reduce motion" choice kept in the browser, and links to the two legal pages. It adds no endpoint.
- **Privacy policy and terms:** two public, static pages with no script. Each says at the top that the project is a demonstration on invented students and that the college must review and adopt the text before real records are used.

## Trade-offs

- A student-facing upload is a larger attack surface than an admin-only one. It is limited by the checks above, by the 2 MB limit, by redrawing the picture, and by the general request limit of 120 a minute. There is still no virus scanning; a redrawn 512 by 512 JPEG leaves very little room for a payload.
- The image code uses the JDK's own `javax.imageio`. No dependency was added. The JDK decoders have had security fixes over the years, so the Java runtime must be kept up to date.
- `img-src` is wider than before by exactly one host. An attacker who could inject markup still could not load a script, and could load an image only from the application or from the project's own bucket.
- Mirrored orientations (EXIF values 2, 4, 5 and 7) are not corrected. Cameras rarely write them.
- A face photo is personal data. The project still runs on synthetic data only; a real deployment needs the owner's decision on OQ-17 and a reviewed privacy policy first.

## Consequences

- `V6__profile_details.sql` adds `bio` and `photo_path` to `student_profiles`. Both are optional, and nothing existing changes.
- `StorageClient` moved from the `resource` package to `common.storage`, because two features now use it.
- The profile response has two more fields, `bio` and `hasPhoto`.
- The photo cannot be shown until the storage bucket exists and `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are set (task `T3-01`). Until then an upload answers `503 STORAGE_UNAVAILABLE` and the page keeps the initials.
- The release checklist gains two manual checks against the real bucket: a photo uploads and shows, and a link stops working after five minutes.
- The owner should read the changed code line by line (SR-48): `OwnProfileService`, `ProfilePhotoProcessor`, `StudentController`, `SecurityConfig.contentSecurityPolicy`.

# Security Rules

These rules are mandatory for all application code and for every person or coding agent that changes it. They are deliberately short. The reasoning behind them is in [docs/11-security-plan.md](docs/11-security-plan.md).

The words **MUST**, **MUST NOT** and **SHOULD** are used as follows: MUST and MUST NOT are absolute; SHOULD means "do this unless there is a recorded reason not to".

If a rule blocks a task, stop and report it. Do not work around the rule.

## 1. Credentials and secrets

- **SR-01** Passwords MUST be stored only as BCrypt hashes produced by Spring Security's `PasswordEncoder`.
- **SR-02** Passwords MUST NOT be stored, logged, returned in a response or written to the audit log in any form. The one exception is a newly generated temporary password, returned once to the administrator who created it.
- **SR-03** The roll number, username or any predictable value MUST NOT be used as a default password.
- **SR-04** Database credentials, the Supabase service key and AI API keys MUST NOT appear in frontend code, in Git, in documentation, in test fixtures or in logs.
- **SR-05** Secrets MUST be read from environment variables. `.env` MUST NOT be committed.
- **SR-06** A secret that has been exposed MUST be rotated. Removing it from the code is not sufficient.

## 2. Authentication and sessions

- **SR-07** Authentication MUST use Spring Security. Custom password checking or home-made session handling MUST NOT be written.
- **SR-08** Session cookies MUST be `HttpOnly`, `Secure` (in production) and `SameSite=Lax`.
- **SR-09** CSRF protection MUST stay enabled for every state-changing request.
- **SR-10** Login failures MUST return the same message whether the username or the password was wrong.

## 3. Authorization

- **SR-11** Every protected endpoint MUST enforce login and role on the server. Hiding a control in the frontend is never sufficient.
- **SR-12** Authorization MUST NOT be bypassed, relaxed or commented out to make a feature or a test work.
- **SR-13** A student identifier supplied by the browser MUST NOT be trusted. The student MUST be derived from the session.
- **SR-14** An owned object MUST be loaded by its ID **and** its owner in the same query.
- **SR-15** A request for a record the user may not see MUST return `404`, the same as for a record that does not exist.
- **SR-16** Students MUST NOT be able to create, change or delete official marks, attendance, results, profiles, notices, resources or questions. No student endpoint may write to those tables.
- **SR-17** Quiz scores MUST be calculated by the server. A score sent by the browser MUST be ignored.
- **SR-18** Correct answers and explanations MUST NOT be sent to the browser before an attempt is submitted.

## 4. Input and data access

- **SR-19** Every request body and parameter MUST be validated on the server for presence, type, length and range.
- **SR-20** SQL MUST use bound parameters. SQL MUST NOT be built by concatenating or interpolating input, including sort columns.
- **SR-21** Entities MUST NOT be returned from controllers or bound directly from requests. DTOs MUST be used.
- **SR-22** Unknown fields in a request MUST be rejected.
- **SR-23** List endpoints MUST be paginated with a maximum page size.

## 5. Output and errors

- **SR-24** Dynamic text MUST be written to the page as text (`textContent`). Server, user or AI data MUST NOT be assigned to `innerHTML`.
- **SR-25** Stack traces, SQL, class names, file paths and secrets MUST NOT be shown to users or returned by the API.
- **SR-26** Inline scripts and inline event handlers MUST NOT be used.

## 6. Files and storage

- **SR-27** Uploads MUST be checked for size, declared type, file signature and parseability before being stored.
- **SR-28** Storage paths MUST be generated by the server. A user-supplied file name MUST NOT be used in a path.
- **SR-29** The storage bucket MUST be private. Private study documents MUST NOT be published through public links.
- **SR-30** File access MUST go through a signed link issued after an authorization check and valid for at most five minutes.
- **SR-31** Uploaded files MUST NOT be saved to, or served from, the application's own file system or origin.

## 7. Database and Supabase

- **SR-32** Row Level Security MUST be enabled on every table.
- **SR-33** The browser MUST NOT talk to Supabase directly, except to fetch a file through a signed link.
- **SR-34** The schema MUST be changed only through Flyway migrations. An applied migration MUST NOT be edited.
- **SR-35** Changes to marks, attendance, results, account status and passwords MUST write an audit entry in the same transaction.
- **SR-36** Audit entries MUST NOT be updated or deleted by application code.

## 8. AI

- **SR-37** AI provider calls MUST be made only from the backend.
- **SR-38** Official records (marks, attendance, results, profiles of any student) MUST NOT be sent to an AI provider.
- **SR-39** AI output MUST be parsed, validated and rendered as plain text. It MUST NOT be executed, trusted as an instruction or used to make an access decision.
- **SR-40** AI MUST NOT score official tests or produce official records.
- **SR-41** Every AI feature MUST enforce its input limits and the per-user quota.

The full AI rules are in [docs/14-AI-security-and-privacy.md](docs/14-AI-security-and-privacy.md).

## 9. Data

- **SR-42** Only synthetic data MUST be used in every environment. Real student information MUST NOT be stored, committed or used in tests.
- **SR-43** Logs MUST NOT contain passwords, session identifiers, tokens, keys, signed URLs or AI prompt and response text.

## 10. Process

- **SR-44** Tests and security controls MUST NOT be disabled, skipped or weakened to obtain a passing build.
- **SR-45** A dependency MUST NOT be added without approval.
- **SR-46** Destructive changes to production (dropping tables, deleting data, rotating production secrets, deploying) MUST NOT be made without explicit authorization from the owner for that specific action.
- **SR-47** A suspected vulnerability MUST be reported privately to the owner, not in a public issue.
- **SR-48** Any change that touches authentication, authorization, uploads, AI or secrets SHOULD be reviewed by the owner before merging.
